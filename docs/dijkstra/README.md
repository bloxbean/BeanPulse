# Dijkstra: BloxBean engineering master reference

**Research baseline: 20 November 2026 · Public sources only · Revision 1**

This reference is the starting point for Dijkstra work in Cardano Client Lib (CCL), Yaci, Yaci Store and Yano. It records what the inspected code does, what is still experimental or gated, and what must be qualified before these projects can claim end-to-end support. It provides design direction and test boundaries, not a final architecture or a promise of mainnet activation.

The central engineering conclusion is that Dijkstra is a coordinated change to transaction construction, binary representations, account accounting and ledger execution. Adding an era enum or Plutus V4 script tag is necessary but insufficient. The most reusable first deliverable is a versioned, cross-repository conformance corpus covering original bytes, identities, transaction levels, validity and account deltas.

## 1. Read this baseline correctly

### 1.1 Evidence classes

Every implementation conclusion in this document belongs to one of these classes. “Confirmed” means present at the specified revision, not mainnet activated or independently production qualified.

| Class | Meaning | Engineering use |
| --- | --- | --- |
| **N — node snapshot** | Confirmed in the ledger/consensus/Plutus dependencies of the published node 11.2.1 prerelease | Primary compatibility target for reproducible integration fixtures |
| **U — later upstream** | Implemented in the inspected upstream ledger after that node snapshot | Track separately; do not silently backport its expected behavior into N tests |
| **G — gated** | Code or representation exists, but a protocol version, parameter, experimental setting or unpublished dependency limits use | Record the gate alongside the feature |
| **P — proposal/planned** | CIP, issue, ADR or open PR expresses intent; shipped behavior is not established | Design input and backlog, not acceptance evidence |
| **X — excluded** | Leios consensus/network/protocol implementation, including ranking/endorsing/vote transport | Outside this report; shared era wire fields remain in scope |

Source precedence is: exact dependency code and its rules/tests; node release and build metadata; current upstream diffs; CDDL; then CIPs and tracking discussions. A CIP can still say “Proposed” after code is implemented. Conversely, a field in CDDL or a parameter in genesis does not prove its economic or consensus behavior is active. Tests named here are source evidence and recommended qualification targets; this research did not run a node, a Haskell solver or the four repositories' test suites.

## 2. Breaking changes and migration priorities

This is the migration checklist to read before feature design. Apply each behavior by era and, where relevant, negotiated protocol version. Preserve historical Conway behavior.

| Change | Before / after | Required response |
| --- | --- | --- |
| Block layout | Conway separates transaction bodies, witness sets, auxiliary data and invalid indexes; Dijkstra carries each transaction together | Replace positional block assumptions; preserve outer order and original byte spans |
| Submission versus block validity | Submitted Dijkstra transaction normally has 3 items; block transaction has 4 with validity last | Use distinct APIs/fixtures; never delete block validity because submission removed it |
| Legacy submission flag | Four-item submission accepts only legacy `true`; `false` is rejected | Stop authoring the flag in Dijkstra; retain Conway authoring and decode transition tests |
| Stake certificate tags 0/1 | Implicit-deposit registration/deregistration disappear from Dijkstra | Emit explicit deposit/refund certificates 7/8 and satisfy their witness rules |
| Redeemers | Conway flat-list compatibility disappears; Dijkstra requires a map | Migrate writers, hash calculations and parsers; test duplicate keys and purpose 6 |
| Witness collections | Several lists become sets and duplicate handling tightens | Do not silently deduplicate invalid received data and then report it valid |
| Required signers | Body key 14 extends from key hashes to guards, including script credentials | Keep the original encoding form and expose full guards; a signer-only projection loses information |
| Nested identities | A block transaction can contain independently identified child bodies | Introduce explicit level and order; keep parent fee, validity and collateral boundaries |
| Accounts | Reward accounts gain direct transaction deposits and balance predicates | Separate direct deposits from rewards, protocol deposits, withdrawals and donations |
| Script representation | V4 has type/hash prefix 4, witness key 8, cost-model language 3 and changed context | Update all enums, hashes, JSON, storage and evaluators coherently |
| Protocol parameters | New keys 34–56, including nullable values and changing key-55 semantics | Preserve unknown values and absent/null/value distinctions; do not use Conway constants as Dijkstra settings |
| Node compatibility | Node 11.2 removes N2C versions below 23 and obsolete local-state queries | Test handshake plus query tags/results; era decoding alone is insufficient |

The binary changes are directly visible in the pinned [Submission and block CDDL](https://github.com/IntersectMBO/cardano-ledger/blob/95b369053fd32422695a81fb7d5289d6dd35eee2/eras/dijkstra/impl/cddl/data/dijkstra.cddl#L1-L34), [Top transaction CDDL](https://github.com/IntersectMBO/cardano-ledger/blob/95b369053fd32422695a81fb7d5289d6dd35eee2/eras/dijkstra/impl/cddl/data/dijkstra.cddl#L113-L148), [Witness/redeemer CDDL](https://github.com/IntersectMBO/cardano-ledger/blob/95b369053fd32422695a81fb7d5289d6dd35eee2/eras/dijkstra/impl/cddl/data/dijkstra.cddl#L862-L899) and [Parameter CDDL](https://github.com/IntersectMBO/cardano-ledger/blob/95b369053fd32422695a81fb7d5289d6dd35eee2/eras/dijkstra/impl/cddl/data/dijkstra.cddl#L680-L760). The removal of certificate tags 5/6 is **not** a new Conway-to-Dijkstra change: they were already absent from Conway. Address encodings, transaction input `[hash,index]`, native-asset identifiers, existing metadata forms, governance action families and most output forms remain recognizable; their enclosing rules and accepted values still require version-aware tests.

## 3. Complete material wire and rule inventory

### 3.1 Block, header and era boundaries

The pinned Dijkstra CDDL describes `block = [header, block_body]` and a body containing a transaction list plus nullable Leios and Peras certificate slots. Each in-block transaction is `[body, witnesses, auxiliary_data_or_null, is_valid]`. Submission is `[body, witnesses, auxiliary_data_or_null]`, with a temporary legacy alternative containing `true` in the old position. The flag is not a child field. A decoder must know whether it is reading submission, a block transaction or a child; array length alone is not a robust API contract. [Submission and block CDDL](https://github.com/IntersectMBO/cardano-ledger/blob/95b369053fd32422695a81fb7d5289d6dd35eee2/eras/dijkstra/impl/cddl/data/dijkstra.cddl#L1-L34) [Ledger transaction decoders](https://github.com/IntersectMBO/cardano-ledger/blob/95b369053fd32422695a81fb7d5289d6dd35eee2/eras/dijkstra/impl/src/Cardano/Ledger/Dijkstra/Tx.hs#L145-L186)

The ledger CDDL header has twelve fields, including advertised maximum protocol major/software tag, a certificate-presence flag and an announcement slot. **The node snapshot still uses Praos for Dijkstra.** Its consensus adapter maps the ten-field Praos header into the ledger's extended header interface with placeholder values. Therefore “Dijkstra has a twelve-field header” is true of the ledger CDDL but is not sufficient to predict bytes from node 11.2.1. Preserve and test both explicitly supported envelopes; do not assume that adopting shared Dijkstra parsing means implementing Leios. [Header CDDL](https://github.com/IntersectMBO/cardano-ledger/blob/95b369053fd32422695a81fb7d5289d6dd35eee2/eras/dijkstra/impl/cddl/data/dijkstra.cddl#L52-L113) [Praos Dijkstra adapter](https://github.com/IntersectMBO/ouroboros-consensus/blob/808e400545729b1246ba4393c69326ec4a04a730/ouroboros-consensus-cardano/src/shelley/Ouroboros/Consensus/Shelley/HFEras.hs#L65-L120)

The outer hard-fork block wrapper uses Dijkstra tag **8**; the header/transaction hard-fork sum and local-state era indexing use **7**. This offset includes Byron's special block constructors. Do not reuse a block-era enum blindly in transaction submission or query wrapping. Consensus permits Dijkstra under supported negotiated versions; the inspected node release supports N2C V23, and its latest released N2N version is V15. Development versions are not a stable compatibility promise. [Consensus versions and wrappers](https://github.com/IntersectMBO/ouroboros-consensus/blob/808e400545729b1246ba4393c69326ec4a04a730/ouroboros-consensus-cardano/src/ouroboros-consensus-cardano/Ouroboros/Consensus/Cardano/Node.hs#L160-L355) [Hard-fork sum indexing](https://github.com/IntersectMBO/ouroboros-consensus/blob/808e400545729b1246ba4393c69326ec4a04a730/ouroboros-consensus-cardano/src/ouroboros-consensus-cardano/Ouroboros/Consensus/Cardano/Block.hs#L260-L302) [Yaci query era](https://github.com/bloxbean/yaci/blob/f1d50e37ac23fdeeb988d626f5b639865b9d1638/core/src/main/java/com/bloxbean/cardano/yaci/core/protocol/localstate/api/Era.java)

Hash and size calculations also change with the unified body. Preserve the block body byte span and use the target implementation's body-hash and wire-size rules; reconstructing a Conway segregated body from mapped objects is incorrect. The node ledger's full-transaction `hashTx` covers body/witness/auxiliary hashes and validity, while ordinary ledger transaction ID remains the body hash. Upstream later replaces this API with a memoized representation. Application UTxO references must continue to use the correct body ID. [Dijkstra block body](https://github.com/IntersectMBO/cardano-ledger/blob/95b369053fd32422695a81fb7d5289d6dd35eee2/eras/dijkstra/impl/src/Cardano/Ledger/Dijkstra/BlockBody/Internal.hs) [Transaction hash/encoding boundary](https://github.com/IntersectMBO/cardano-ledger/blob/95b369053fd32422695a81fb7d5289d6dd35eee2/eras/dijkstra/impl/src/Cardano/Ledger/Dijkstra/Tx.hs#L440-L533) [Ledger 0.6 development changes](https://github.com/IntersectMBO/cardano-ledger/blob/fc91132b23b561dcb428d12865e9c573d5ecc577/eras/dijkstra/impl/CHANGELOG.md#L1-L115)

### 3.2 Transaction bodies, witnesses and scripts

| Surface | Dijkstra delta | Consequence |
| --- | --- | --- |
| Body key 14 | Bare key-hash set or ordered credential set (“guards”) | Preserve form for hash fidelity; script credentials introduce validation without a spend/mint/withdrawal trigger |
| Body key 23 | Nonempty ordered set of child transactions | Order is semantically significant; one level of nesting only |
| Body key 24 | Nonempty map from required top-level guard credential to datum or null | Allowed in top and child bodies in actual CDDL; enforce appropriate datum presence and guard satisfaction |
| Body key 25 | Nonempty reward-account-to-coin map | Direct ADA deposits into registered accounts |
| Body key 26 | Account balance intervals at the current execution level | Checks observe effects of earlier children, before the current level's changes |
| Body key 27 | Starting account intervals, top only | Checks the account snapshot before the entire batch |
| Child body | Omits fee, collateral inputs/return/total, further children and key 27 | Never construct a child by serializing an unrestricted ordinary top-level transaction |
| Witness keys 0/1/2/4 | Nonempty sets for vkey, native, bootstrap and datum witnesses | Duplicate rejection and original encoding matter |
| Witness key 8 | Nonempty V4 scripts | Carry through parsing, script hashes, script lookup, storage and evaluation |
| Redeemer purpose 6 | Guarding | Extend purpose-to-script resolution; index is level-local |
| Native script type 6 | Require a guard credential | Native and Plutus authorizations can be composed without a dummy action |
| Script reference type 4 | Plutus V4 | Hash with prefix 4, retain original script bytes and wrapper distinctions |
| Tagged auxiliary map key 5 | V4 scripts | Auxiliary scripts are another representation surface, not automatically executable witnesses |

Authority: [Top transaction CDDL](https://github.com/IntersectMBO/cardano-ledger/blob/95b369053fd32422695a81fb7d5289d6dd35eee2/eras/dijkstra/impl/cddl/data/dijkstra.cddl#L113-L148) [Child and account CDDL](https://github.com/IntersectMBO/cardano-ledger/blob/95b369053fd32422695a81fb7d5289d6dd35eee2/eras/dijkstra/impl/cddl/data/dijkstra.cddl#L820-L875) [Script CDDL](https://github.com/IntersectMBO/cardano-ledger/blob/95b369053fd32422695a81fb7d5289d6dd35eee2/eras/dijkstra/impl/cddl/data/dijkstra.cddl#L382-L453) [Witness/redeemer CDDL](https://github.com/IntersectMBO/cardano-ledger/blob/95b369053fd32422695a81fb7d5289d6dd35eee2/eras/dijkstra/impl/cddl/data/dijkstra.cddl#L862-L899) [Auxiliary/certificate CDDL](https://github.com/IntersectMBO/cardano-ledger/blob/95b369053fd32422695a81fb7d5289d6dd35eee2/eras/dijkstra/impl/cddl/data/dijkstra.cddl#L916-L945). Child maps exclude keys 2, 13, 16, 17, 23 and 27; top and child both permit key 24. This code-level fact overrides older narrative descriptions that imply required top-level guards appear only in children.

Other material CDDL differences are easy to miss: the multiasset map must now be nonempty; bootstrap witness chain code is exactly 32 bytes; VRF output is exactly 64 bytes; protocol-version proposal bounds extend to 13; pool parameters optionally include a BLS public key/proof pair of 96/48 bytes, including the legacy absent/null alternatives. Preserve certificate serialization without implementing Leios voting. [Value/script hash CDDL](https://github.com/IntersectMBO/cardano-ledger/blob/95b369053fd32422695a81fb7d5289d6dd35eee2/eras/dijkstra/impl/cddl/data/dijkstra.cddl#L180-L215) [Header CDDL](https://github.com/IntersectMBO/cardano-ledger/blob/95b369053fd32422695a81fb7d5289d6dd35eee2/eras/dijkstra/impl/cddl/data/dijkstra.cddl#L52-L113) [Certificate and pool CDDL](https://github.com/IntersectMBO/cardano-ledger/blob/95b369053fd32422695a81fb7d5289d6dd35eee2/eras/dijkstra/impl/cddl/data/dijkstra.cddl#L453-L505) [Witness/redeemer CDDL](https://github.com/IntersectMBO/cardano-ledger/blob/95b369053fd32422695a81fb7d5289d6dd35eee2/eras/dijkstra/impl/cddl/data/dijkstra.cddl#L862-L899)

CDDL is not the entire acceptance specification. At decoder version 12, the binary library accepts chunked/indefinite byte and text strings in places using the general decoders. Record, set, datum, value and redeemer decoders impose additional versioned constraints. A parser that checks only shape may accept invalid duplicate collections or reject legal alternate encodings. A model round trip may normalize bytes that were valid and signed. Conformance must distinguish decoding acceptance, rule validity, byte preservation and canonical writer output. ## 4. Nested transactions and guards

### 4.1 What nesting enables

Nested transactions let independent participants prepare and sign constrained transaction bodies which an assembler places into one atomic top-level transaction. This enables composition, sponsorship and batching without requiring each child to carry a fee/collateral bundle or balance independently. A child can require top-level guards so that the final assembly must satisfy an authorization policy. This is materially different from submitting several ordinary transactions in a loop. CIP-118 describes the intent; the rules are the authority for the exact snapshot. [CIP-118](https://github.com/cardano-foundation/CIPs/blob/03387471681166e746518d58a33e25f2ccea3d29/CIP-0118/README.md) [Ordered child transitions](https://github.com/IntersectMBO/cardano-ledger/blob/95b369053fd32422695a81fb7d5289d6dd35eee2/eras/dijkstra/impl/src/Cardano/Ledger/Dijkstra/Rules/SubLedgers.hs) [Batch UTXO checks](https://github.com/IntersectMBO/cardano-ledger/blob/95b369053fd32422695a81fb7d5289d6dd35eee2/eras/dijkstra/impl/src/Cardano/Ledger/Dijkstra/Rules/Utxo.hs#L325-L435)

Conceptually, a sponsor can assemble two signed children with complementary asset flows, add top-level inputs/change and pay the batch fee. The overall value equation must balance. The top-level body commits to the embedded children, including their witnesses; changing a child's witness after the parent has been signed changes the parent body and invalidates its signature. A child's own ID and signatures depend on its own body, not the parent's fee. This makes “finish child witnesses, then freeze and sign the parent” a critical construction boundary. [CCL Dijkstra ADR 0004](https://github.com/bloxbean/cardano-client-lib/blob/d90602ea1d5c3f95c57192e36b6c1bd87eb857e7/transaction-spec/adr/0004-dijkstra-in-the-transaction-model.md) [Child witness checks](https://github.com/IntersectMBO/cardano-ledger/blob/95b369053fd32422695a81fb7d5289d6dd35eee2/eras/dijkstra/impl/src/Cardano/Ledger/Dijkstra/Rules/SubUtxow.hs#L230-L277) [Dijkstra transaction bodies](https://github.com/IntersectMBO/cardano-ledger/blob/95b369053fd32422695a81fb7d5289d6dd35eee2/eras/dijkstra/impl/src/Cardano/Ledger/Dijkstra/TxBody.hs)

This does not allow an arbitrary tree or a chain of freshly created UTxOs inside one batch. Children are a flat ordered collection. The top rule checks all batch spending/reference/collateral inputs against the **original** UTxO, and each level also checks currently unspent inputs to prevent cross-child or child/parent double spends. A child cannot spend an output another child just created. Self-usable *scripts* under CIP-172 are a different capability from spending newly created *outputs*. [Batch UTXO checks](https://github.com/IntersectMBO/cardano-ledger/blob/95b369053fd32422695a81fb7d5289d6dd35eee2/eras/dijkstra/impl/src/Cardano/Ledger/Dijkstra/Rules/Utxo.hs#L325-L435) [Child UTXO transition](https://github.com/IntersectMBO/cardano-ledger/blob/95b369053fd32422695a81fb7d5289d6dd35eee2/eras/dijkstra/impl/src/Cardano/Ledger/Dijkstra/Rules/SubUtxo.hs#L225-L270) [Upstream scripts and pool witnesses](https://github.com/IntersectMBO/cardano-ledger/blob/fc91132b23b561dcb428d12865e9c573d5ecc577/eras/dijkstra/impl/src/Cardano/Ledger/Dijkstra/UTxO.hs#L180-L235)

### 4.2 Execution order and atomicity

The ledger captures original UTxO and account state, processes children in order, then processes the top-level transaction. Thus parent-last is the ledger effect order even though the parent contains the children in its serialized body. Every level has its own body, witnesses, auxiliary data, local validity interval, redeemer indexes and output indexes. The top level owns the fee, collateral and overall phase-2 validity. [Children before parent](https://github.com/IntersectMBO/cardano-ledger/blob/95b369053fd32422695a81fb7d5289d6dd35eee2/eras/dijkstra/impl/src/Cardano/Ledger/Dijkstra/Rules/Ledger.hs#L390-L485) [Ordered child transitions](https://github.com/IntersectMBO/cardano-ledger/blob/95b369053fd32422695a81fb7d5289d6dd35eee2/eras/dijkstra/impl/src/Cardano/Ledger/Dijkstra/Rules/SubLedgers.hs)

```text
Original UTxO and account snapshot
        |
        v
child[0] -> child[1] -> ... -> child[n-1] -> top-level effects
        |                 batch-wide phase-2 outcome
        +---------------------------------------------+
        valid: commit all normal effects
        invalid: commit only top-level collateral effects
```

Each child is validated with local witness requirements, metadata and script-integrity data. Script availability is shared through the batch's script cache, but signatures and spending datum obligations are not simply pooled into one bag. The top transaction accounts for the entire batch's execution units and maximum transaction size. The rules collect/evaluate phase-2 scripts across the batch. A failed child script does not produce a partly successful batch or a separately invalid child transaction. On phase-2 invalidity, child normal effects are not applied and the top collateral path governs. Phase-1 failure rejects the transaction rather than creating a collateral-only success. [Child witness checks](https://github.com/IntersectMBO/cardano-ledger/blob/95b369053fd32422695a81fb7d5289d6dd35eee2/eras/dijkstra/impl/src/Cardano/Ledger/Dijkstra/Rules/SubUtxow.hs#L230-L277) [Child UTXO transition](https://github.com/IntersectMBO/cardano-ledger/blob/95b369053fd32422695a81fb7d5289d6dd35eee2/eras/dijkstra/impl/src/Cardano/Ledger/Dijkstra/Rules/SubUtxo.hs#L225-L270) [Batch UTXO checks](https://github.com/IntersectMBO/cardano-ledger/blob/95b369053fd32422695a81fb7d5289d6dd35eee2/eras/dijkstra/impl/src/Cardano/Ledger/Dijkstra/Rules/Utxo.hs#L325-L435) [Batch transaction operations](https://github.com/IntersectMBO/cardano-ledger/blob/95b369053fd32422695a81fb7d5289d6dd35eee2/eras/dijkstra/impl/src/Cardano/Ledger/Dijkstra/Tx.hs#L194-L344)

For persistence, use **outer block position** and **child position** separately. A child's output index starts at zero within its body; it is not the concatenated output offset across the batch. Its UTxO reference is its own body ID plus local output index. Preserve the parent ID and child ordinal as provenance and uniqueness context. Do not infer a child's identity from parent ID plus output offset, or expose it as an independently submitted transaction without stating that it belongs to an atomic batch. Repeated/replayed observations need idempotent storage keyed to the same inclusion and rollback boundary. [Child UTXO transition](https://github.com/IntersectMBO/cardano-ledger/blob/95b369053fd32422695a81fb7d5289d6dd35eee2/eras/dijkstra/impl/src/Cardano/Ledger/Dijkstra/Rules/SubUtxo.hs#L225-L270) [Yaci transaction mapper](https://github.com/bloxbean/yaci/blob/f1d50e37ac23fdeeb988d626f5b639865b9d1638/core/src/main/java/com/bloxbean/cardano/yaci/core/model/serializers/TransactionBodySerializer.java) [CCL SubTransaction](https://github.com/bloxbean/cardano-client-lib/blob/d90602ea1d5c3f95c57192e36b6c1bd87eb857e7/transaction-spec/src/main/java/com/bloxbean/cardano/client/transaction/spec/SubTransaction.java)

### 4.3 Guards, required guards and legacy mode

CIP-112's original “observe” idea appears in implementation as **guarding**. A script credential in key 14 can cause validation without consuming a script UTxO, minting a token or making a dummy withdrawal. Native script constructor 6 can require a guard credential. Key 24 lets a level require a top-level guard and supply its datum. This is how a child can constrain the final aggregate transaction rather than merely hope the assembler behaves correctly. Do not label a guard as a required key signer when it is a script credential. [CIP-112](https://github.com/cardano-foundation/CIPs/blob/03387471681166e746518d58a33e25f2ccea3d29/CIP-0112/README.md) [Guards and native scripts](https://github.com/IntersectMBO/cardano-ledger/blob/95b369053fd32422695a81fb7d5289d6dd35eee2/eras/dijkstra/impl/src/Cardano/Ledger/Dijkstra/Scripts.hs) [Dijkstra guard/witness rules](https://github.com/IntersectMBO/cardano-ledger/blob/95b369053fd32422695a81fb7d5289d6dd35eee2/eras/dijkstra/impl/src/Cardano/Ledger/Dijkstra/Rules/Utxow.hs)

The exact guard datum rules and legacy restrictions should be ported from the target rules, including malformed/missing guard datums and required top-level guard satisfaction. Regular V4 validation sees the current level's `TxInfo`; a top-level guarding script additionally sees `TopTxInfo`, containing child contexts, guard-specific datums, starting account intervals and a simplified batch aggregate. A child guard does not receive that top-level aggregate. [Top guard aggregate and starting intervals](https://github.com/IntersectMBO/cardano-ledger/blob/95b369053fd32422695a81fb7d5289d6dd35eee2/eras/dijkstra/impl/src/Cardano/Ledger/Dijkstra/TxInfo.hs#L840-L925) [Plutus V4 context types](https://github.com/IntersectMBO/plutus/blob/261766ad1d582bce8c86bad1af7a3b0e5355b21c/plutus-ledger-api/src/PlutusLedgerApi/V4/Contexts.hs#L349-L505)

Old Plutus versions do not gain the V4 context. In the node snapshot, top-level old-language use selects legacy-mode restrictions: the top must satisfy its own value-conservation equation as well as the full batch equation, and new account/guard context features are restricted. Children cannot execute old Plutus as though it were V4. The implementation's legacy path is more nuanced than the broad prohibition still found in parts of the CIP narrative. Preserve compatibility by testing explicit legal and illegal combinations; do not globally reject every nested batch containing a legacy top-level script or globally allow every new field. [Batch UTXO checks](https://github.com/IntersectMBO/cardano-ledger/blob/95b369053fd32422695a81fb7d5289d6dd35eee2/eras/dijkstra/impl/src/Cardano/Ledger/Dijkstra/Rules/Utxo.hs#L325-L435) [Legacy and V4 context translation](https://github.com/IntersectMBO/cardano-ledger/blob/95b369053fd32422695a81fb7d5289d6dd35eee2/eras/dijkstra/impl/src/Cardano/Ledger/Dijkstra/TxInfo.hs#L480-L630) [Ledger Imp/UtxoSpec.hs](https://github.com/IntersectMBO/cardano-ledger/blob/95b369053fd32422695a81fb7d5289d6dd35eee2/eras/dijkstra/impl/testlib/Test/Cardano/Ledger/Dijkstra/Imp/UtxoSpec.hs)

### 4.4 QuickTx construction: a design direction, not an existing API

CCL's ADR 0004 explicitly separates experimental model work from a later QuickTx milestone. No ready-made nested QuickTx API is established in the inspected release. Existing batch submission APIs in Yano are also not evidence of on-chain nested construction. [CCL Dijkstra ADR 0004](https://github.com/bloxbean/cardano-client-lib/blob/d90602ea1d5c3f95c57192e36b6c1bd87eb857e7/transaction-spec/adr/0004-dijkstra-in-the-transaction-model.md) [yano #239](https://github.com/bloxbean/yano/issues/239)

An eventual builder should make these stages visible:

1. Build each child with an explicit Dijkstra era and a child-only field set. Resolve its own spending witnesses, redeemers, metadata and interval. Allow deliberate imbalance while reporting its asset contribution.
2. Add required top-level guards and their data before the child body is signed. Compute the child's script-integrity hash using the correct language views and local redeemers.
3. Finish and freeze the child body and witnesses. Preserve its original encoded form if accepting externally signed children; report whether a model conversion would rewrite it.
4. Assemble the ordered children. Resolve shared script availability, original-state inputs/accounts, aggregate budget and reference-script accounting. Fund the full batch and choose top-level collateral.
5. Evaluate against the selected node/ledger baseline, calculate the final top-level fee, freeze the parent body, then sign and submit the three-item Dijkstra form.

This order avoids accidental signer invalidation and gives a sponsor a clear responsibility boundary. It is not a recommendation to add hidden auto-balancing across participants' already signed children. Design choices still needing an ADR include immutable signed-child objects, identity retention, guard datum ownership, error attribution to child index and whether evaluation can return structured per-level results.

### 4.5 Indexing and storage choices

There are three plausible storage approaches; the report does not prescribe a final schema.

| Approach | Advantage | Cost / invariant to resolve |
| --- | --- | --- |
| Separate child table joined to outer transaction | Keeps existing outer transaction pagination and fee/validity ownership clear; child indexes can be explicit | Every input/output/certificate/script/account relation needs level-aware joins; avoid duplicating parent fields inconsistently |
| Unified transaction-level table with parent/level/ordinal | Reuses relation machinery for top and child entities | Existing transaction counts, “latest transactions”, unique hashes and submission endpoints need carefully versioned semantics |
| Preserve raw batch plus JSON children initially | Fast lossless ingestion and replay foundation | Insufficient alone for child UTxO lookups, asset history, reward-account activity and efficient address queries |

A useful invariant is `(chain inclusion, outer ordinal, level, child ordinal)` plus the body's actual hash, with parent linkage and effective validity. Store the original bytes for audit/reprocessing. The ordinary transaction endpoint can retain outer transactions by default and expose children through an explicit expansion or child endpoint; this is a recommendation, not current Store behavior. Count endpoints should state whether they count outer transactions, transaction levels or outputs. Rollback must remove child rows, joins, account deltas and derived aggregates atomically with the parent and recover prebatch UTxO/account state. A raw-only phase can be acceptable as an ingestion milestone only if it does not falsely mark child indexing complete.

## 5. Direct deposits and reward-account accounting

### 5.1 Meaning and developer use

CIP-159 phase 1 makes ADA account balances directly usable by transactions. Body key 25 credits a reward/account address using value supplied by the transaction. It is not an epoch reward and is not a refundable protocol deposit. A developer can fund a registered account without creating a new spendable UTxO for that amount, then use account withdrawals under the new rules in later transactions. The inspected implementation is ADA/coin-only; multiasset account extensions discussed in the broader issue are not established here. [CIP-159](https://github.com/cardano-foundation/CIPs/blob/03387471681166e746518d58a33e25f2ccea3d29/CIP-0159/README.md) [Account transition order](https://github.com/IntersectMBO/cardano-ledger/blob/95b369053fd32422695a81fb7d5289d6dd35eee2/eras/dijkstra/impl/src/Cardano/Ledger/Dijkstra/Rules/Entities.hs#L275-L343) [cardano-ledger #5501](https://github.com/IntersectMBO/cardano-ledger/issues/5501)

| Operation | Value movement | How an API should describe it |
| --- | --- | --- |
| Direct deposit, key 25 | Transaction value into an account balance | Transaction-origin account credit, with parent/child provenance |
| Withdrawal, key 5 | Account balance into transaction value | Account debit; preserve credential witness and original-balance constraints |
| Protocol deposit/refund | Registration/proposal obligation into or out of the deposit accounting pot | Certificate/proposal deposit and refund, not account funding |
| Epoch reward | Reward calculation credits an account | Reward-origin credit, with epoch/source |
| Treasury donation, key 22 | Transaction value into treasury | Donation; not an account credit or withdrawal |
| Treasury withdrawal/refund at epoch boundary | Governance/refund state transitions | Separate origin and effective epoch, even when the destination is an account |

The account receiving a direct deposit must exist **after certificates at that level** and match the network. Register-and-deposit in the same level is therefore meaningful. Balance checks occur before that level's withdrawals, certificates and direct deposits. The transition applies withdrawals, then certificates, then direct deposits. A deposit must be included in the produced side of value conservation. A model that merely copies key 25 into a list but omits it from balancing will produce incorrect fees/change or an invalid transaction. [Account transition order](https://github.com/IntersectMBO/cardano-ledger/blob/95b369053fd32422695a81fb7d5289d6dd35eee2/eras/dijkstra/impl/src/Cardano/Ledger/Dijkstra/Rules/Entities.hs#L275-L343) [Direct-deposit value accounting](https://github.com/IntersectMBO/cardano-ledger/blob/95b369053fd32422695a81fb7d5289d6dd35eee2/eras/dijkstra/impl/src/Cardano/Ledger/Dijkstra/UTxO.hs#L100-L147)

### 5.2 Per-level versus starting balance intervals

Key **26** checks the account balance immediately before the current level's changes, after preceding children have run. Key **27** appears only at the top and checks the original snapshot before the whole batch. Bounds are lower-inclusive/upper-exclusive; one bound may be null, or the value may be an exact coin amount. Both-null is not a valid unconstrained interval. Missing accounts and wrong networks have explicit failure cases. [Balance interval validation](https://github.com/IntersectMBO/cardano-ledger/blob/95b369053fd32422695a81fb7d5289d6dd35eee2/eras/dijkstra/impl/src/Cardano/Ledger/Dijkstra/Rules/Entities.hs#L455-L517) [Child and account CDDL](https://github.com/IntersectMBO/cardano-ledger/blob/95b369053fd32422695a81fb7d5289d6dd35eee2/eras/dijkstra/impl/cddl/data/dijkstra.cddl#L820-L875)

For example, an account starts with 100 ADA. Child 0 deposits 20 ADA. Child 1 can require an exact current balance of 120 via key 26. The top can simultaneously require an exact starting balance of 100 via key 27. These are different assertions, not duplicate spellings. In normal mode, aggregate withdrawals across top and children are capped by the original account balance, so the new 20 ADA cannot be used to justify withdrawing 120 within the same batch. Legacy-mode withdrawal rules differ and must be tested separately. [Original-balance withdrawal rules](https://github.com/IntersectMBO/cardano-ledger/blob/95b369053fd32422695a81fb7d5289d6dd35eee2/eras/dijkstra/impl/src/Cardano/Ledger/Dijkstra/Rules/Entities.hs#L345-L405)

**Script visibility:** regular V4 `TxInfo` exposes direct deposits and key-26 intervals. It does not contain key 27. However, a **top-level guarding script** receives key 27 through `TopTxInfo.topTxInfoStartingAccountBalanceIntervals`; a subtransaction guard does not receive `TopTxInfo`. Saying “starting intervals are invisible to V4” would be incorrect. ### 5.3 CCL and Store exposure

CCL already has experimental direct-deposit and interval fields. Its model reuses a withdrawal-shaped list for direct deposits, which is a representation convenience, not a reason to present deposits as withdrawals. A public builder should offer explicit deposit and account-condition intents, require the network/account identity, expose the three timing concepts (original, before current level, after level), and include deposits in balancing. Backend parameter/account suppliers and evaluators need matching support. An account query returning only “rewards earned” is not a reliable substitute for current spendable account balance. [CCL TransactionBody](https://github.com/bloxbean/cardano-client-lib/blob/d90602ea1d5c3f95c57192e36b6c1bd87eb857e7/transaction-spec/src/main/java/com/bloxbean/cardano/client/transaction/spec/TransactionBody.java) [CCL balance interval](https://github.com/bloxbean/cardano-client-lib/blob/d90602ea1d5c3f95c57192e36b6c1bd87eb857e7/transaction-spec/src/main/java/com/bloxbean/cardano/client/transaction/spec/AccountBalanceInterval.java)

Store needs an account activity record with origin, amount, transaction level, account address, slot/block and effective validity. A dedicated direct-deposit table/event is a natural option; a general signed account-delta table is an alternative if it preserves origins and query compatibility. Reusing `WithdrawalProcessor` as a structural guide is reasonable; reusing its debit semantics or writing deposits into the rewards table is not. The account aggregate must consume direct credits once, remove them on rollback, and reconcile with epoch rewards, certificate refunds and withdrawals. Reward totals must not count user-funded deposits as yield. It must not double count a direct deposit both in transaction balance and epoch reward application. Cross-repository fixtures should contain account starting state, per-level deltas, ending state and reversed state, not only CBOR and JSON snapshots.

## 6. Plutus V4, reference scripts and evaluators

### 6.1 Context and representation

V4 is introduced at PV12 in the pinned Plutus library. Its context is a new contract: local transaction ID and optional child index; local inputs/reference inputs/outputs; mint, certificates, withdrawals and direct deposits; balance intervals; validity range; guards and required top-level guards; redeemers/data; voting/proposals and treasury fields. It has **no ordinary `txInfoFee` field**. `ScriptContext` includes the current script's hash. Guarding adds purpose 6 and specialized top-level information. A V3 context with an extra enum tag is not V4. [Plutus language activation](https://github.com/IntersectMBO/plutus/blob/261766ad1d582bce8c86bad1af7a3b0e5355b21c/plutus-ledger-api/src/PlutusLedgerApi/Common/Versions.hs#L90-L124) [Plutus V4 context types](https://github.com/IntersectMBO/plutus/blob/261766ad1d582bce8c86bad1af7a3b0e5355b21c/plutus-ledger-api/src/PlutusLedgerApi/V4/Contexts.hs#L349-L505) [Legacy and V4 context translation](https://github.com/IntersectMBO/cardano-ledger/blob/95b369053fd32422695a81fb7d5289d6dd35eee2/eras/dijkstra/impl/src/Cardano/Ledger/Dijkstra/TxInfo.hs#L480-L630)

Representation changes also extend below `TxInfo`. V4 uses list encodings for several product types such as transaction output references, asset classes, rational values and governance structures through `ListEncoded`; do not carry over constructor wrappers indiscriminately from V3. Conversely, the inspected `V4.Value` module reexports V1's `Value` representation and specializes `AssetClass`; the presence of value builtins does not prove that every V4 context value has become a native `BuiltinValue`. Keep ledger CBOR, Plutus Data encoding and evaluator-internal value representation separate. [V4 list encoding](https://github.com/IntersectMBO/plutus/blob/261766ad1d582bce8c86bad1af7a3b0e5355b21c/plutus-ledger-api/src/PlutusLedgerApi/V4/Internal.hs#L15-L44) [V4 Value representation](https://github.com/IntersectMBO/plutus/blob/261766ad1d582bce8c86bad1af7a3b0e5355b21c/plutus-ledger-api/src/PlutusLedgerApi/V4/Value.hs#L20-L64) [V4 output-reference representation](https://github.com/IntersectMBO/plutus/blob/261766ad1d582bce8c86bad1af7a3b0e5355b21c/plutus-ledger-api/src/PlutusLedgerApi/V4/Tx.hs#L45-L90)

Pointer addresses are another boundary: Dijkstra checks collateral-return pointers and V4 context translation rejects pointer-containing outputs it cannot represent. Avoid a blanket claim that all historical pointer addresses disappear from the chain. Keep old-era decoding, new output validation and context translation as distinct tests. [Batch UTXO checks](https://github.com/IntersectMBO/cardano-ledger/blob/95b369053fd32422695a81fb7d5289d6dd35eee2/eras/dijkstra/impl/src/Cardano/Ledger/Dijkstra/Rules/Utxo.hs#L325-L435) [V4 address translation](https://github.com/IntersectMBO/cardano-ledger/blob/95b369053fd32422695a81fb7d5289d6dd35eee2/eras/dijkstra/impl/src/Cardano/Ledger/Dijkstra/TxInfo.hs#L650-L690)

### 6.2 Cost models and actual evaluator path

V4 cost models use language key **3**; script references/hash prefixes use **4**. These numbers belong to different namespaces. The pinned ledger's initial V4 cost-model count is provisionally **251**, explicitly annotated as subject to change before the hard fork. Its parameter-name and evaluation-context wiring still uses the V3 API, and its V4 execution wrapper deserializes/evaluates through V3 functions while supplying a V4 context. The standalone Plutus V4 API separately specifies its own ordered `V4.ParamName` list and semantics variant G. This is a concrete snapshot integration caveat, not a basis to assume either “V4 is absent” or “the final V4 evaluator contract is settled.” [Pinned V4 cost wiring](https://github.com/IntersectMBO/cardano-ledger/blob/95b369053fd32422695a81fb7d5289d6dd35eee2/libs/cardano-ledger-core/src/Cardano/Ledger/Plutus/CostModels.hs#L295-L360) [Pinned V4 execution wiring](https://github.com/IntersectMBO/cardano-ledger/blob/95b369053fd32422695a81fb7d5289d6dd35eee2/libs/cardano-ledger-core/src/Cardano/Ledger/Plutus/Language.hs#L580-L603) [V4 evaluation context contract](https://github.com/IntersectMBO/plutus/blob/261766ad1d582bce8c86bad1af7a3b0e5355b21c/plutus-ledger-api/src/PlutusLedgerApi/V4/EvaluationContext.hs#L21-L46)

Similarly, N's Dijkstra script type has V4 constructors but reports `eraMaxLanguage = PlutusV3`; U corrects that to V4. Treat this as an explicit discrepancy to cover with language discovery and execution fixtures. Do not turn it into an unsupported claim that all V4 execution is disabled, since the actual constructors, translation and evaluation path are present. [Pinned V4 language discrepancy](https://github.com/IntersectMBO/cardano-ledger/blob/95b369053fd32422695a81fb7d5289d6dd35eee2/eras/dijkstra/impl/src/Cardano/Ledger/Dijkstra/Scripts.hs#L475-L500) [Upstream V4 maximum](https://github.com/IntersectMBO/cardano-ledger/blob/fc91132b23b561dcb428d12865e9c573d5ecc577/eras/dijkstra/impl/src/Cardano/Ledger/Dijkstra/Scripts.hs#L475-L495)

Never alphabetically sort a parameter map into an execution vector or use the old CDDL “223 V3 parameters” comment as the V4 contract. Yano's julc/Aiken/Scalus adapters and Store submission evaluation need explicit capability checks for V4 context, semantics and costs; a `PlutusV4Script` Java class alone establishes none of these.

### 6.3 Builtins and protocol gates

The pinned Plutus source clearly separates implemented builtins from released availability. Batch 6—including array operations, exponentiation, BLS multi-scalar multiplication and value operations—belongs to PV11 (van Rossem) availability, even when Dijkstra release notes mention updated costs. It should not all be presented as newly introduced by Dijkstra. Batch 7 (`MultiIndexArray`, `Policies`, `AssetCount`, `KeepPolicies`, `DropPolicies`) is mapped to `futurePV`, not PV12, for all four languages. UPLC 1.2.0 is enabled at PV12 in the pinned version table; V4 accepts UPLC 1.0.0, 1.1.0 and 1.2.0. Post-Dijkstra builtin semantics are F for V1/V2 and G for V3/V4. ## 7. Rewards, certificates and other ledger changes

### 7.1 Withdrawals, pledge leverage and pool margin

**CIP-181 (N):** a reward withdrawal no longer requires delegation to a registered DRep or predefined voting option. The new account transition validates network, account existence, balance and witnesses without Conway's governance-participation prerequisite. Wallets can stop injecting an otherwise unnecessary voting-delegation action for Dijkstra withdrawals; they must retain the Conway rule for historical validation and existing-era construction. [CIP-181](https://github.com/cardano-foundation/CIPs/blob/03387471681166e746518d58a33e25f2ccea3d29/CIP-0181/README.md) [Account transition order](https://github.com/IntersectMBO/cardano-ledger/blob/95b369053fd32422695a81fb7d5289d6dd35eee2/eras/dijkstra/impl/src/Cardano/Ledger/Dijkstra/Rules/Entities.hs#L275-L343)

**CIP-50 (N/G):** `maxPledgeLeverage` is included in the reward calculation. It limits the stake supported by a pool's pledge in the reward formula; null keeps the leverage cap disabled. An SPO/delegator-facing projection must show the selected parameter and epoch, not predict a new yield from the existence of key 38. Store's reward/adapot calculation and Yano's epoch processing require differential reward fixtures with null, zero and positive leverage, under-pledged pools and boundary rounding. CCL/Yaci primarily preserve/query the parameter unless they themselves calculate rewards. [CIP-50](https://github.com/cardano-foundation/CIPs/blob/03387471681166e746518d58a33e25f2ccea3d29/CIP-0050/README.md) [Pinned reward path](https://github.com/IntersectMBO/cardano-ledger/blob/95b369053fd32422695a81fb7d5289d6dd35eee2/eras/shelley/impl/src/Cardano/Ledger/Shelley/Rewards.hs#L295-L390) [Pledge-leverage formula](https://github.com/IntersectMBO/cardano-ledger/blob/95b369053fd32422695a81fb7d5289d6dd35eee2/libs/cardano-ledger-core/src/Cardano/Ledger/State/SnapShots.hs#L135-L175)

**CIP-23 requires a split conclusion.** N contains `minPoolMargin`, but its pool rule still rejects registration below `minPoolCost`, and its inspected reward path does not yet apply the new minimum-margin clamp. Earlier readiness notes described later intra-era behavior. U removes the `StakePoolCostTooLowPOOL` rejection and clamps effective cost and margin in reward calculation for PV12 and above. That later implementation supersedes the old planning description in upstream, but is not proof of adoption by node 11.2.1 or the newer source tags. Model the parameter now; choose reward/certificate behavior from the exact target revision. ### 7.2 Stake snapshots and epoch order

Dijkstra takes the stake snapshot after pool/governance refunds and treasury withdrawals at the epoch transition so SPO and DRep voting stake account for the same effects. An indexer that independently reconstructs stake/rewards or a replay engine that checkpoints before these changes can diverge even if transaction parsing is correct. Add boundary fixtures with retiring pools, expired proposals, treasury withdrawals and accounts receiving refunds, then compare stake, reward and rollback state. Certificate tags 7/8 use explicit deposit/refund quantities where tags 0/1 were previously convenient. Builders must use current protocol values and match credential authorization. Pool registration serialization must preserve optional BLS fields. The detailed governance action families are largely carried forward; Dijkstra-specific top/child processing and changed state order are the new obligations. No wholesale rewrite of unchanged voting/proposal encodings is justified, but child governance identity, order and rollback need qualification. ### 11.3 Replay, rollback and downstream API behavior

Replay must begin with the original UTxO/account snapshot for each batch, apply children in order then top effects, and commit atomically according to the top validity result. A rollback journal needs sufficient information to reverse child-created outputs, consumed original outputs, account credits/debits, certificates and governance effects. It should not depend on looking up a later chain state to reconstruct a child's reference-script or account context. Archive records should retain body bytes and level provenance even when a presentation API flattens selected information.

Protocol parameters and evaluator caches are historical state. Replaying a block with today's cost model or the later upstream reward rules produces an invalid comparison. Proposal serialization/reload also needs its original era; the existing governance codec is an explicit audit target because era-less readers can choose Conway for ambiguous data. Shadow replay output should identify parent and child index, rule failure, script purpose/hash, target protocol version and the exact baseline revision. [Yano governance persistence](https://github.com/bloxbean/yano/blob/9370f5a321a0d47cb0555fb6c4422c808bb245c5/ledger-state/src/main/java/org/yanoproject/ledgerstate/governance/GovernanceCborCodec.java) [Yano shadow replay](https://github.com/bloxbean/yano/blob/9370f5a321a0d47cb0555fb6c4422c808bb245c5/tx-services/src/main/java/org/yanoproject/tx/ShadowBundleReplay.java) [Yano parameter resolution](https://github.com/bloxbean/yano/blob/9370f5a321a0d47cb0555fb6c4422c808bb245c5/tx-services/src/main/java/org/yanoproject/tx/ProtocolParamsResolution.java)

The transaction API should distinguish “decoded”, “phase-1 validated”, “phase-2 evaluated” and “ledger applied” capability. Existing off-chain batch-submission tests do not establish on-chain nested transaction support. A Dijkstra child is not independently submitted, and its fee/validity should not be fabricated by an API mapper. Existing Conway clients should continue receiving their established transaction shapes unless opting into an explicitly versioned richer response.

## 12. Shared conformance fixtures and staged dependencies

### 12.1 A single fixture contract

The four projects should share test data, not necessarily a single runtime domain model. CCL can own byte/schema fixtures; Yaci maps them to wire events; Store proves indexed/query state; Yano proves ledger transitions and replay. Each fixture should carry: source repository and commit, node/build/dependency versions, network/genesis hash, era/PV, negotiated protocol version where relevant, exact CBOR, original hashes, expected normalized model, initial state, expected outcome/failure and ending/reverted state. Record whether bytes are synthetic, Haskell-generated or observed on-chain.

| Fixture family | Must distinguish | Consumers |
| --- | --- | --- |
| Envelope / hashes | Conway versus Dijkstra; submission/block/child; block tag 8 versus era 7; ten/twelve-field headers; original bytes versus model bytes | CCL, Yaci, Yano, Store raw ingestion |
| Decoder acceptance | Indefinite strings/containers, set duplicates, map redeemers, fixed lengths, empty multiasset maps, trailing data | CCL/Yaci first; Yano rule boundary |
| Nested balance / identity | Two child IDs with output index zero; parent-last; no fresh-output spending; local signatures; whole-batch fees/budgets | All four |
| Guards / scripts | Key/hash versus credential guards; native constructor 6; purpose 6; required guard datums; top versus child context | CCL, Yano; Yaci/Store representation |
| Accounts | Direct credits versus rewards/refunds; key 26 versus 27; original withdrawal cap; registration/network/interval errors | All four, with state assertions in Store/Yano |
| Validity / collateral | Phase-1 rejection; phase-2 invalid batch; no child effects; top collateral return and fee ownership | All four |
| V4 / costs | Hash prefix, witness/aux/reference sources, exact Data encoding, cost vector order, historical PV and future builtins | CCL/Yano evaluators; Yaci/Store persistence |
| Parameters / epoch | New keys, absent/null/value, tier boundaries, leverage cap, snapshot timing, N/U margin differences | CCL suppliers, Yaci queries, Store/Yano state |
| Upstream divergence | CIP-172, supplemental datums, invalid-path checks, batch ref fees, language maximum, pool changes | Separate N/U manifests, never one blended expectation |
| Migration / rollback | Conway history, fork boundary, schema upgrade, restart, nested rollback and epoch reversal | Yaci events, Store, Yano |

A passing parser test proves neither fee correctness nor database completeness. A successful node submission proves neither final inclusion validity nor correct rollback. Acceptance evidence should name its layer and observed outcome. Existing CCL Dijkstra vectors include older generated material; regenerate from the chosen contemporary Haskell baseline before treating them as the release oracle.

### 12.2 Recommended delivery stages

1. **Freeze targets and evidence.** Select the exact node binary/ledger revision and DijkstraNet genesis/parameters; obtain the solved plan for any newer source tag. Publish a compatibility manifest with explicit N/U gates. Reconcile upstream readiness #5604 and the four existing project trackers.
2. **Shared byte foundation.** Qualify CCL's tables/raw views and model identity boundaries; produce immutable cross-repository fixtures. Publish the compatible CCL/Yaci pair and verify dependency convergence, not merely source merges.
3. **Lossless ingestion and node API.** Qualify Yaci block/transaction mapping, V23 query/submission behavior and event provenance. Store/Yano can preserve raw Dijkstra data while keeping incomplete semantic capabilities explicit.
4. **State and indexing.** Implement transaction levels, direct-deposit/account deltas, V4/guard relationships, parameter history and atomic rollback in Store; implement equivalent ledger/replay transitions in Yano. Resolve the child storage ADR before freezing public API shapes.
5. **Construction and execution.** Add QuickTx nested/guard/deposit workflows once child immutability, fee calculation, signing and V4 evaluation are proven against the selected node. Expose precise unsupported capabilities during the transition.
6. **End-to-end qualification.** Run DijkstraNet submission/inclusion, clean replay, rollback/restart, parameter/epoch transitions and historical Conway regression suites. Only then declare scoped support with a published capability matrix.

## 13. Gaps, uncertainties and maintenance rules

These are concrete limits of the evidence, not reasons to defer the foundations:

* **No mainnet activation or final parameter claim.** DijkstraNet PV12 is established; mainnet date and final economic values are not qualified by this review.
* **Newer source-tag build plans remain unqualified.** Source/CHaP pins and package constraints were inspected; 11.2.2/11.2.3 were not solved/built and are not substituted for the explicit 11.2.1 dependency inventory.
* **N is not U.** Ledger master `fc91132b23b561dcb428d12865e9c573d5ecc577` contains substantial changes after the node pin, with a 0.6.0.0 development changelog. Do not call them node-shipped without a new dependency manifest.
* **V4 integration has snapshot caveats.** The pinned ledger uses V3 execution/cost helpers for V4 context and reports an old maximum-language value; upstream fixes only some of this in the inspected diff. Exact evaluator qualification remains a release prerequisite.
* **Reference-input charging is not proven active.** Key 55 changes units/naming upstream, and the inspected fee paths do not establish the proposed multiasset/datum charge. Preserve the parameters and track implementation before pricing transactions with them.
* **CIP/issue text can lag code.** CIPs remain Proposed; readiness issues include completed and unfinished children; PR bodies can describe superseded drafts. This report prioritizes pinned code and separately records status observations.
* **Artifact publication is a separate gate.** Yaci #244 is merged but absent from published pre16; Store/Yano adoption remains incomplete. GitHub release tags were checked, but every Maven/Docker artifact was not independently downloaded and checksum-audited.
* **No end-to-end execution was performed here.** Repository tests and PR-reported results are identified as such. This is a source audit and implementation reference, not certification of any of the four projects.
* **Leios/Peras semantics are intentionally bounded.** Shared wire/parameter/certificate preservation is covered. Consensus scheduling, ranking/endorsement/voting transport and performance qualification are not.
