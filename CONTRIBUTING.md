# Contributing to BeanPulse

BeanPulse changes should keep the dashboard easy to operate, safe to publish, and
consistent across every monitored project.

## Development workflow

1. Create a focused branch from the current default branch.
2. Make the smallest coherent code or configuration change.
3. Refresh data when project or release behavior changed.
4. Review the affected pages locally.
5. Run the verification suite.
6. Open a PR describing the user-visible result and operational impact.

```bash
npm run data:refresh
npm run dev
npm run verify
```

Use Node.js 24 or later. The project intentionally has no runtime dependencies,
package installation step, or build framework.

## What to review locally

For project or data changes, check:

- The organization project directory.
- The Available projects catalog, selection state, and tracking-request link.
- The project's Overview page.
- Its Releases directory and at least one release detail page.
- The Unassigned lane.
- Pull request and issue search and filters.
- Narrow-screen layout when the UI changed.

Do not hand-edit `data/projects.json`. It is generated by
`npm run data:refresh`. Large snapshot diffs should be reviewed for unexpected
private information, incorrect repositories, or major count changes.

## Project configuration changes

- Keep slugs unique and stable because they are used in shared URLs.
- Use the official project name and repository path.
- Write short product descriptions.
- Choose an accent color with readable contrast.
- Verify that a project without version metadata has a useful Unassigned view.
- Confirm a watched project no longer appears in the Available projects catalog.

See [Project and roadmap configuration](docs/CONFIGURATION.md).

## Roadmap changes

Roadmap outcomes should:

- Describe a capability or user result rather than repeat a PR title.
- Explain the value in plain language.
- Link only the PRs and issues that implement that outcome.
- Stay small enough to scan quickly.
- Avoid claiming work is shipped before the linked implementation confirms it.

## Code changes

- Preserve the dependency-free static architecture unless a reviewed requirement
  justifies changing it.
- Escape repository-sourced text before rendering it as HTML.
- Keep query-parameter links working on GitHub Pages.
- Do not expose tokens or require browser-side GitHub authentication.
- Add or update unit tests for release detection and status-summary logic.
- Keep collection limits explicit when adding API requests.

## Pull request checklist

- [ ] The change has a clear user or maintainer benefit.
- [ ] `npm run verify` passes.
- [ ] Relevant local views were checked.
- [ ] Generated data was refreshed when required.
- [ ] No credentials or private repository information were added.
- [ ] Documentation reflects configuration or operational changes.
- [ ] API usage and Pages behavior were considered.
